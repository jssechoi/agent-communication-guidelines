# 메일 형식 (Mail Format)

`SKILL.md` §5 에서 메일 형식으로 정한 문서에 적용합니다. 합쇼체로 쓰고, 문서 구성은
`document-rules.md` 를 함께 적용합니다.

## M1. 문의 회신 골격

문의에 답하는 회신에 적용합니다. 운영 안내문과 서술형 보고서는 D7 에 따라 목적에 맞는 구조를 고릅니다.

```markdown
### 1. [대주제 1]

**저희가 이해한 문의 의도**: [질문자가 확인하려는 목적과 전제 조건]

[결론: 예 - "네, 전제 조건대로 구성됩니다."]
[근거와 설명]
- **(세부 주제 A)**: 기술·정책 설명
- **(세부 주제 B)**: 기술·정책 설명

* 관련 문서: [공식 문서 링크]

---

### 선제적 제안 및 보완 사항

- **[개선 영역]**: 확인한 현상 -> 개선 방안
```

- 선제적 제안 절은 근거가 있는 제안이 있을 때만 두고, 1~3건으로 제한합니다. 제안한 작업을 직접 실행하지는 않습니다.
- 영어 상황이면 같은 구조를 영어로 바꿔 영어 단일 문서로 씁니다.

## M2. 문서 어조

독자 관계에 맞춰 어조를 고릅니다. 사용자가 지정한 문체와 기존 문서의 격식 수준이 우선합니다.

| 문서 | 어조 | 표현 |
| :--- | :--- | :--- |
| 분석·자문 보고서(서술형) | 독자가 판단할 근거를 주는 차분한 자문 | 사실 `~했습니다`, 해석 `~로 볼 수 있습니다`, 조건부 전망 `~하면 ~할 가능성이 있습니다`, 권고 `[대상]은 [사항]을 확인할 필요가 있습니다` |
| 운영·절차 안내 | 담당 업무와 독자의 행동을 알리는 정중하고 직접적인 안내 | `[담당자]가 [업무]를 수행합니다`, `[대상]은 [조건]에 [행동]해 주시면 됩니다`. 준비된 사항과 독자가 할 일을 구분 |
| 기술 조사·비교 | 조사 대상과 확인 범위를 설명하는 중립적 서술 | 용어 정의 → 분류 → 공통 기준의 비교 → 확인 범위 안의 판단. `~입니다`와 `~이다` 중 하나로 통일 |

- 표의 어미는 기능별 예시입니다. 문장마다 어미를 바꿔 끼우거나 `~로 보입니다`를 일괄 추가하지 않습니다. 사실·추론·권고가 구분되면 같은 종결이 반복되어도 그대로 둡니다.
- 행위 주체가 의미를 바꾸면 주어를 남깁니다(운영팀의 준비와 발표자의 제출). 처리 상태가 중요한 문장에는 `~로 제공됩니다` 같은 수동형도 씁니다.
- `따라서`는 인과, `다만`은 제한, `한편`은 논점 전환이 실제로 있을 때 씁니다. 같은 뜻에는 같은 용어를 쓰고, 설명이 필요한 용어만 처음에 풀이합니다.
- 장황한 겸양 표현, 상투적인 당부, 반복 요약은 쓰지 않습니다.

## M3. 내부 관리 메타데이터 배제

수신자에게 가는 최종본(HTML, 메일 본문, 상위 보고서)에는 결론과 그 근거만 둡니다. 아래는 본문에서 제거합니다.

- **조직 추정과 일정 메모**: `[조직명]은 등재된 적이 없는 조직명입니다`, `회신은 [부서]에서 받았고 기한은 [날짜]입니다`처럼 담당 부서를 추정하거나 내부 마감을 나열한 메모
- **문서 관리 규칙**: `이 페이지는 조회용입니다`, `값이 어긋나면 md를 따릅니다`처럼 문서 형상 관리나 충돌 예방 지침
- **저장소 지도**: 로컬 파일 구조나 문서 경로 목록
- **인덱스 규칙**: 라벨 인용 규칙, 위치 매핑 표 같은 내부 추적용 코드
- **패키징 사양**: `외부 요청 없음`, `자립형 단일 HTML`처럼 수신자가 쓰지 않는 동작 사양

## 점검

- [ ] 문의 회신은 `저희가 이해한 문의 의도:`로 전제를 확인하고, 주제마다 `관련 문서:`를 달았는가?
- [ ] 요청에는 대상·기한·행동·제출 경로가 있는가(D9)?
- [ ] 최종본에 M3 의 내부 메타데이터가 남아 있지 않은가?
